# WorkSpec Board — Architecture & Code Review

**Reviewed at:** commit `56fc1e5` (main), 2026-09-04
**Scope:** `index.html`, `app.js`, `core/*`, `state/*`, `ui/*`, `utils/*`, `style.css`, plus `SPEC.md`, `SKILL.md`, `PROMPT.md` and the demo `.workspec/` repository.
**Method:** full read of every source file against the three governing documents, followed by targeted probes of the YAML engine under Node (findings marked **confirmed** were reproduced; the rest were established by reading the code paths).

---

## Summary

This is a well-built reference implementation. The layering (`utils → core → state → ui → app`) is clean, the file-system abstraction is real (every read/write goes through `WorkspecFS`), the surgical `status:` patch honours the "change nothing else" rule literally, loading is fault-tolerant, and the editor's focus-stable in-place refresh is the right call for a framework-free app. Comments consistently cite the spec section they implement, which makes the code unusually easy to audit.

The risks are concentrated in two places:

1. **Data safety in the YAML engine.** The parser fails *silently* instead of loudly in several cases (stray indentation truncates the document, trailing comments and flow mappings are absorbed into string values, backslashes double on every save). Because the editor re-serializes from the parsed object, each of these turns into a lossy write. This contradicts SPEC §15/§17 ("save without data loss") and PROMPT §11 ("never silently fail").
2. **Lost-update paths between the store and the editor.** The editor keeps a private working copy that is not told when the underlying record changes (drag/drop of the open card) and navigation discards the working copy even when the flush-save failed.

Secondary concerns: there are **no automated tests** for a codebase whose most delicate parts (`yaml.js`, `parser.js`, `ids.js`) are pure functions; the board is rebuilt from scratch on every state change including each search keystroke, which will not scale to the 2,000-item target in PROMPT §8; and the required fallback file-import mode (PROMPT §3.3, §7) does not exist.

**Top five actions, in order:**

1. Make the YAML engine lossless-or-loud, with a round-trip guard that locks lossy items to raw editing (§1.2 A1, §4 items 1, 4, 5).
2. Version records in the store and make the editor rebind on external change; abort navigation when a flush-save fails (§1.2 A2, §4 items 2, 3).
3. Add a Node test harness with a fixture corpus for `utils/` and `core/` — no build step required (§1.2 A3).
4. Stop full-board re-renders on every emit; parallelize repository loading (§1.2 A4).
5. Adopt per-clone ID blocks plus a validator to end ID collisions (§3).

## 1. Architecture

### 1.1 What is working well

- **Dependency direction is strictly one-way.** `utils` know nothing about the DOM; `core` knows nothing about the store; `ui` only talks to the store. This is exactly the shape PROMPT §6 asks for.
- **`WorkspecFS` is a genuine seam.** Handle caching means a save never re-walks the tree, and nothing outside `core/filesystem.js` touches the File System Access API.
- **Two write paths for two intents.** Metadata/body edits re-serialize; drag/drop patches one line. This is the right split and it is documented in the README's guarantees.
- **Failure isolation on load.** A bad file becomes a card with an error badge rather than a failed board.
- **Deliberate rendering strategy.** Board and sidebar are cheap to rebuild and are rebuilt; the editor is expensive to rebuild and is refreshed in place. Scroll and caret preservation show the trade-off was understood.
- **Small, readable surface.** ~2,400 lines of JS with no dependencies. Nothing is over-abstracted.

### 1.2 Recommended architectural changes

| # | Change | Improves | Effort |
|---|--------|----------|--------|
| A1 | Lossless-or-loud YAML engine with a round-trip guard | Functionality (data safety) | Medium |
| A2 | Single source of truth for the open record (versioning + rebind) | Functionality | Small |
| A3 | Test harness for pure modules, no build step | Maintainability | Small |
| A4 | Incremental board rendering and parallel loading | Performance | Medium |
| A5 | Split `app.js`; move item-creation logic into `core` | Maintainability | Small |
| A6 | Second filesystem backend + persisted directory handle | Functionality | Medium |
| A7 | Central field schema driving form, coercion and validation | Maintainability, extensibility | Medium |
| A8 | Dialog/toast semantics and keyboard reachability | Functionality (accessibility) | Small |

#### A1. Make the YAML engine lossless-or-loud

The engine's design goal is "preserve everything", but its failure mode is "drop things quietly". Three changes fix this as a class rather than case by case:

1. **Strict parse.** In `parseMapping`, an unexpected deeper indent (`utils/yaml.js:200`) and a line that is not `key: value` (`utils/yaml.js:204`) must throw, not `break`/`continue`. A thrown error already routes to `record.errors` via `parseItem`, which makes the card non-editable in form view and never re-serialized — exactly the safe outcome.
2. **Round-trip guard on load.** After parsing, compute `stringifyYaml(parseYaml(fm))` and compare it to the source front matter with whitespace and comment lines normalized. If they differ in *content* (not just formatting), flag the record `lossy: true`. The editor then opens such items in raw-YAML mode only, and `saveItem` writes the raw text verbatim. This one check catches every unsupported construct (flow mappings, anchors, multi-document, unusual quoting) without having to enumerate them.
3. **Symmetric scalar escaping.** `parseScalar` and `serializeScalar` must be exact inverses for the quoting they produce. Today the serializer escapes `\` but the parser never unescapes it (§4 item 4).

Optionally, keep standalone `#` comment lines by recording them as ordered pseudo-entries (`{ __comment: '...' }`) that the serializer emits back. This closes the README's stated limitation cheaply because the object already preserves insertion order.

#### A2. One source of truth for the open record

The editor's working copy (`ui/editor.js:68-79`) is only refreshed when `record.path` changes. Any other mutation of the same record — today `moveItem` — is invisible to it. Recommended:

- Add `record.version` (an integer bumped by `saveItem`, `moveItem`, `addItem`, and by reload). The editor's `_bind` key becomes `path + version`; when the version changes and the working copy is clean it rebinds; when it is dirty it merges only the fields the external change touched (for `moveItem`, `status`) and shows a notice.
- Make `save()` return `true|false`. `openItem`, `onOpenContext`, `createItem` and `refreshRepository` must stop when it returns `false` instead of proceeding to `store.open()` and silently discarding the buffer.
- Delete `state.dirty` from the store (`state/store.js:28`) or make it the only dirty flag. Right now it is never set to `true`, so it is a second, always-wrong source of truth.

#### A3. Tests without a build step

The absence of tests is the largest maintainability gap. Because each module is an IIFE that takes `window.WS`, it can be loaded in Node with a three-line shim (this review used exactly that to reproduce the YAML defects). Recommended:

- Wrap each module as `(function (WS) { ... })(typeof window !== 'undefined' ? (window.WS = window.WS || {}) : (module.exports))` — or keep the IIFE and load with `new Function('window', src)` from a tiny `test/load.js`. Either way the browser path is unchanged.
- Use the built-in `node --test` runner. Zero dependencies, consistent with PROMPT §3.
- Seed a fixture corpus under `test/fixtures/items/` covering: every scalar form, block scalars, nested namespaces, comments, CRLF line endings, BOM, and each of the defects listed in §4. Every fixture gets a round-trip assertion (`serialize(parse(x))` content-equals `x`).
- Add a `tools/validate-workspec.js` CLI over the same modules (see §3, Layer 2); it doubles as an integration test and as a Git hook.

#### A4. Incremental rendering and parallel loading

`store.subscribe` (`app.js:58-63`) rebuilds the entire board and sidebar on every emit. Emits happen per search keystroke, per filter change, per toast message, and per save. At 2,000 items that is 2,000 card constructions plus `facets()` (four passes over all items) per keystroke.

Recommended, in increasing order of effort:

1. **Memoize derived selectors.** Cache `facets()` and `filteredItems()` keyed on `(items version, filters, sort)`. Cheap and removes most redundant work.
2. **Debounce the search input** (~80 ms) in `ui/sidebar.js:45`.
3. **Keyed card reconciliation.** Keep a `Map<path, {version, element}>` in `BoardView`; on render, reuse the element when `version` is unchanged and only move it between columns. Card DOM then stops being rebuilt at all except for the edited card.
4. **Slice the state.** Emit separate events (`items`, `selection`, `filters`, `message`) so a toast does not repaint the board. Only do this after 1-3 if profiling still shows a problem.
5. **Parallel loading.** `loadRepository` reads items sequentially (`core/model.js:124-131`). Use `Promise.all` over batches of ~32 files; on a local disk this is typically a 5-10× improvement on the "board in under one second" target.

#### A5. Split `app.js` and move domain logic into `core`

`app.js` (428 lines) currently owns repository lifecycle, two dialogs, the context overlay, theme, scroll preservation, overlay/toast plumbing and keyboard handling. Suggested split, keeping the same global-namespace pattern:

```
app.js                 wiring only (subscribe, mount, keyboard)
app/theme.js           storedTheme/setTheme/applyTheme/toggleTheme
ui/overlay.js          showOverlay/closeOverlay/showToast
ui/dialogs.js          openCreateDialog, confirmDelete
core/factory.js        createItemMeta(template, title, model, local) → {meta, body}
```

`createItem` (`app.js:195-244`) contains pure domain rules (canonical ordering, required-field seeding, default assignee) that belong next to `CANONICAL_ORDER` in `core` where they can be unit-tested and reused by a CLI or agent.

#### A6. A second filesystem backend and a remembered directory

PROMPT §3.3 and §7 require a fallback import mode; only the File System Access backend exists, so Firefox and Safari show a banner. Recommended:

- Define the backend contract explicitly (`open, ensurePermission, listFiles, readFile, writeFile, exists, deleteFile`) and add `MemoryFS`: populated from `<input type="file" webkitdirectory>`, read-only in the UI, with an "Export changed files" action that downloads a zip (a ~150-line store-only zip writer is enough; no compression needed). This also gives tests an in-memory backend.
- Persist the `FileSystemDirectoryHandle` in IndexedDB. Handles are structured-cloneable; on next load, list "recent repositories" and reopen with a single permission prompt instead of a directory picker. This is the single largest day-to-day UX win available (see §2, F1).

#### A7. Central field schema

Knowledge about fields is spread across `REQUIRED_FIELDS`/`CANONICAL_ORDER` (`core/parser.js`), `ARRAY_FIELDS`/`KNOWN_TYPES`/`PRIORITIES`/`READONLY_FIELDS` (`ui/editor.js`), the `coerce()` helper, and the `PRIORITY_RANK` map (`core/model.js`). Introduce `core/schema.js`:

```js
const FIELDS = {
  id:       { type: 'string', required: true, readonly: true },
  title:    { type: 'string', required: true },
  status:   { type: 'enum', required: true, values: (model) => model.workflow },
  priority: { type: 'enum', values: ['critical','high','medium','low'], rank: {...} },
  estimate: { type: 'number' },
  labels:   { type: 'list' },
  created:  { type: 'date', required: true, readonly: true },
  // ...
};
```

The form picks widgets from `type`, coercion uses the declared type (fixing the "title `2024` becomes a number" defect), validation and sorting read the same table, and `board.yaml` can extend it (`settings.fields:`) — which is how PROMPT §13's "custom metadata fields without modifying core logic" becomes real.

#### A8. Dialog and toast semantics

Small, contained fixes: give the overlay `role="dialog"` and `aria-modal`, trap focus and restore it on close; give the toast `role="status"` / `aria-live="polite"`; associate sidebar `<label>`s with their selects (`for`/`id`); make Enter submit the create dialog. Drag/drop already has a keyboard alternative (the status select in the editor) — say so in the README.

## 2. Feature enhancements

### F1. Remember repositories and reopen instantly

Persist directory handles in IndexedDB (see A6). On load, show a "Recent" list in the empty state; clicking one calls `requestPermission()` and loads without the picker. Optionally auto-reopen the last repository. Removes the most repetitive step in every session.

### F2. Relationship-aware board and editor

Relationships are the spec's core idea (SPEC §10) but the UI only renders the parent breadcrumb.

- In the editor, render `parent`, `depends_on`, `blocks`, `related` and `context` as clickable chips (open the item / open the context doc), with an "add" picker filtered by ID/title.
- Validate references: an ID that does not exist becomes a warning on the item; a `context` name with no matching file likewise.
- On cards, show a **blocked** badge when any `depends_on` item is not in the last workflow column, and a count of children on EPIC cards.
- Add a board mode "Group by epic" (swimlanes by `parent`), configurable in `board.yaml` `settings.group_by`.

### F3. Change-on-disk detection and conflict-safe saves

Git-native means files change underneath the app (pull, checkout, an agent editing). Today the app will overwrite them.

- Poll `file.lastModified` of the open item every few seconds and on `window` focus; show a banner "changed on disk — Reload / Keep mine".
- In `saveItem` and `moveItem`, read the file first and compare to `record.raw`; if it differs, refuse the write and show the same banner (optimistic concurrency).
- A lightweight "repository changed" check on focus (compare the `items/` listing) with a one-click reload keeps the board honest after a `git pull`.

### F4. Archive instead of delete

SPEC §5 defines `.workspec/archive/` but nothing uses it, and the only removal path is a permanent delete. Add an **Archive** action that moves the file to `archive/` (content untouched), an "Archive all items in *Done*" bulk action, and a sidebar toggle to show archived items read-only. Keep hard delete behind a secondary action.

### F5. Keyboard-first navigation and a command palette

PROMPT §9.3 asks for keyboard navigation; today only Tab/Enter/Esc/Ctrl+S exist.

- Arrow keys move between cards and columns; `[` / `]` move the focused card to the previous/next status (same surgical write as drag/drop); `Enter` opens; `n` creates; `/` focuses search.
- A `Ctrl+K` palette that lists items by ID/title, context docs and actions ("Move to Review", "Toggle preview", "Archive").
- In the editor, a side-by-side live Markdown preview instead of the toggle, so the caret is never lost when previewing.

*Honourable mentions:* honour `settings.card_fields` from `board.yaml` (declared in the demo config but ignored by `ui/board.js`); WIP limits per column in `workflow.yaml` with an over-limit column style; a **Revert** button in the editor (there is currently no way to discard edits).

## 3. The ID collision problem

### 3.1 The problem, precisely

`nextId` (`utils/ids.js:36`) returns `max(existing) + 1` for the type, computed from the files on the local checkout. Two engineers on separate branches who each create a story both get `STORY-000011`. When the branches meet:

- **Same type, same number:** Git reports an add/add conflict on `items/STORY-000011.md`. Not silent, but painful: someone must renumber one item, rename its file, and find every reference to it (`parent`, `depends_on`, `blocks`, `related`, commit messages, PR descriptions), all while SKILL.md tells agents never to renumber.
- **Silent variants:** a rebase or squash-merge resolved with "take theirs", or an agent that resolves the conflict by keeping one side, drops a work item without anyone noticing. Nothing in the app or the repo detects that two files claim the same ID, or that a reference points at nothing.
- **Cross-type:** `STORY-000011` and `TASK-000011` do not collide (sequences are per type), so that case is fine.
- **Same person, two machines:** one engineer working from a PC and a Mac on unsynced branches collides with themselves. The unit that collides is therefore the **working copy** (clone), not the person; any prevention scheme has to be keyed on the clone.

Constraints the solution must respect: SPEC §7.2 (six zero-padded digits, unique, immutable, filename equals ID), SPEC G5 (minimize merge conflicts), SKILL.md ("do not renumber work items"), and PROMPT §15 (no git integration in the app).

### 3.2 Options considered

| Option | Collision-free? | Spec-compatible? | Drawbacks |
|--------|-----------------|------------------|-----------|
| Central counter file (`config/sequence.yaml`) | No | Yes | Both branches still compute the same next value; every creation now also conflicts on the counter file. Worse than today. |
| Random six-digit numbers | Mostly | Yes | Birthday-paradox collisions (~0.2% at 2,000 items per type), loses chronological ordering, unreadable. |
| ULID / UUID IDs (`STORY-01J8X…`) | Yes | **No** (breaks §7.2) | Requires a major spec revision; IDs stop being memorable. Reasonable for a v2.0 discussion only. |
| Provisional IDs renumbered at merge | Yes, eventually | Yes | Renumbering is exactly what SKILL.md forbids; references written before merge go stale. |
| Per-author ID blocks (sharded sequences) | No | Yes | Collision-free between people, but the same person on two machines still collides; needs a user identity. |
| **Per-clone allocator blocks** | **Yes** | **Yes** | One registry line per clone (committed) plus a block number in the git-ignored local config; IDs are no longer globally consecutive. |
| Per-computer postfix (`STORY-001000rd1`) | Only with a registry | **No** (breaks §7.2) | Still needs a registry to keep postfixes unique; breaks the six-digit format, filename sorting and every `TYPE-\d{6}` consumer; numbers stop being unique across the project. |
| Detection + repair tooling only | No | Yes | Necessary but not sufficient; still leaves a manual renumber on every collision. |

### 3.3 Recommendation: per-clone allocator blocks, backed by detection and repair

Three layers. The first prevents collisions; the second makes any remaining collision (misconfiguration, an agent ignoring the rule) fail loudly before merge; the third makes the fix mechanical.

#### Layer 1 — Prevention: per-clone allocator blocks

Every working copy that creates items owns a numeric block per type. Blocks never overlap, so two clones can never generate the same ID no matter how their branches diverge. The spec already provides the per-clone hook: `config/user.local.yaml` is git-ignored and lives inside the clone, so a block number stored there is naturally per working copy. A person with two machines has two clones, two local files and two blocks. Two people sharing one machine have separate OS accounts and clones, so they are covered as well.

**Configuration** (a v1.1 spec extension; the default keeps today's behaviour):

```yaml
# .workspec/config/board.yaml  (committed)
id_allocation:
  strategy: block               # sequential (default) | block
  block_size: 1000
```

```yaml
# .workspec/config/id-blocks.yaml  (committed registry of claimed blocks)
blocks:
  - { block: 1, owner: rdagum, label: windows-pc }   # STORY-001001 … STORY-001999
  - { block: 2, owner: rdagum, label: macbook }      # STORY-002001 … STORY-002999
  - { block: 3, owner: alice,  label: laptop }
  - { block: 9, owner: claude, label: ci-agent }     # an AI agent is just another allocator
```

```yaml
# .workspec/config/user.local.yaml  (git-ignored, one per clone)
handle: rdagum
id_block: 2
```

The registry must be committed: uniqueness of the block numbers is what makes the scheme collision-free, and the registry is the only place that uniqueness can be checked.

**Algorithm** (`utils/ids.js`):

```js
function nextId(type, existingIds, { block = null, blockSize = 1000 } = {}) {
  const upper = String(type).toUpperCase();
  const lo = block == null ? 1 : block * blockSize + 1;
  const hi = block == null ? 999999 : (block + 1) * blockSize;
  let max = lo - 1;
  for (const id of existingIds) {
    const p = parseId(id);
    if (p && p.type === upper && p.number >= lo && p.number <= hi && p.number > max) max = p.number;
  }
  if (max + 1 > hi) throw new Error(`ID block ${block} is exhausted for ${upper}; allocate a new block in users.yaml.`);
  return formatId(upper, max + 1);
}
```

With `block = null` this is exactly today's function, so `strategy: sequential` repositories are untouched.

**Rules and edge cases:**

- Block 0 (`000001–000999`) is the legacy block: every existing item stays where it is. No migration and no renumbering on adoption.
- If a repository already has more than `block_size` legacy items, they simply occupy blocks 0..k. The validator (Layer 2) rejects assigning a block that already contains items, so a new user is given a higher block.
- Six digits give 999 blocks of 1,000 per type. A block is per *clone*, not per branch, so even a team where everyone has two machines uses a handful of blocks; when a block runs out the error tells the user to claim another one.
- **Claiming a block.** When `strategy: block` is set and the local file has no `id_block`, the create dialog offers "Claim a block": the app picks the lowest unclaimed number, appends the registry line, writes `user.local.yaml`, and reminds the user to commit the registry change. Two clones claiming at the same time both append at the same place in `id-blocks.yaml`, which Git reports as a conflict rather than merging silently; the validator also rejects duplicate block numbers.
- **No block configured** under `strategy: block` is a hard stop in the create dialog with the claim action offered inline; silently generating a collidable ID is the thing we are trying to remove. Under `strategy: sequential` nothing changes.
- `SKILL.md` gains one rule under *Creating New Work Items*: "If `id_allocation.strategy` is `block`, generate the ID inside the block named by `id_block` in `user.local.yaml` (or the agent's own registry entry). Never allocate outside your block. If no block is configured, stop and ask."
- The create dialog already previews the generated ID; show the block owner and label next to it ("STORY-002007 · rdagum / macbook") so the scheme is visible rather than magical.

Sorting by ID no longer means sorting by creation time. The board already sorts by `created`/`updated` (configured in `board.yaml`), so nothing in the UI depends on ID order.

#### Layer 2 — Detection: validate uniqueness in the app and in Git

1. **In the app.** `loadRepository` should index items by `meta.id` as well as by path and report: duplicate IDs across files (error on both), filename/ID mismatch (already a warning; promote to error), references to non-existent IDs (warning), duplicate block numbers in `id-blocks.yaml` (error), a local `id_block` that is not in the registry (error), and a claimed block that already contains items owned by another allocator (error). Today `nextId` is computed from file names (`app.js:197`) while validation reads `meta.id`; the two must agree.
2. **`tools/validate-workspec.js`.** A zero-dependency Node script that loads `utils/yaml.js`, `utils/ids.js` and `core/parser.js` through the same shim used for tests, walks `.workspec/items`, applies the checks above, prints one line per problem and exits non-zero. Because it reuses the app's own parser it can never disagree with the board.
3. **Git hooks.** `.githooks/pre-commit` runs the validator on the staged tree; enable with `git config core.hooksPath .githooks` (documented in the README). This catches a wrong block or a hand-written duplicate before it leaves the machine.
4. **CI on the merge result.** Run the validator in the pull-request workflow. GitHub Actions checks out the *merge* commit for `pull_request` events, so a collision between the branch and `main` fails the check even though neither side is wrong on its own. For hosts that check out the branch head, run `git merge-tree --write-tree origin/main HEAD` and validate that tree instead.

With Layer 1 in place, Layer 2 fires only on misconfiguration, so it stays quiet in daily use.

#### Layer 3 — Repair: a mechanical renumber

Collisions from before adoption, or from a misconfigured client, still need fixing. `tools/renumber.js OLD-ID NEW-ID`:

- Renames `items/OLD-ID.md` to `items/NEW-ID.md` and patches its `id:` line surgically (reusing `patchScalarLine`).
- Rewrites every reference in every item's `parent`, `depends_on`, `blocks`, `related` fields, and, with `--body`, whole-word mentions in Markdown bodies.
- Prints the list of changed files so the result is one focused commit.

Policy, added to `SKILL.md` and the README: **renumber only the side that has not reached `main`.** IDs on `main` are immutable; the branch adapts. This is the sanctioned exception to "never renumber", and it applies only to IDs that were never merged.

### 3.4 Alternatives rejected

**Random or UUID-style IDs.** It would work, and it removes the registry, but it breaks SPEC §7.2 and every downstream consumer that relies on six-digit IDs, it makes IDs unreadable in conversation, and it turns filenames into noise in `git log`. The block scheme delivers the same guarantee within the existing format at the cost of one registry line per clone. Keep UUID-style IDs on the table for a 2.0 spec if the registry proves too heavy in practice.

**Per-computer postfix** (`STORY-001000rd1`). Semantically this is the block scheme with the allocator written into the string instead of encoded in the number range, so it provides no guarantee that blocks do not already provide, and it still needs a registry to keep postfixes unique. It costs more: it breaks §7.2, the `ID_RE` in `utils/ids.js`, filename sorting and every consumer that matches `TYPE-\d{6}`; numbers stop being unique across the project, so `STORY-000012rd1` and `STORY-000012mac` both read as "story 12" in conversation and commit messages; and the boundary between number and postfix is ambiguous to the eye. Its only advantage, never exhausting, is not a practical concern at 999 blocks per type.

**Per-author blocks** (the first draft of this proposal). Correct between people, but the same person on two machines still collides. Keying on the clone fixes that with the same mechanism.
