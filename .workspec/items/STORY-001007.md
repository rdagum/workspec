# Summary

Three small behaviours that make a focused epic usable as a project view: new work lands in the epic, an epic can be focused from its own editor, and the focused board flags dependencies that live outside it.

# Business Context

A filtered view hides context. The work most likely to hold an epic up is a dependency in another epic, which the focus filters out, so the view needs to point at it. New work created while looking at an epic almost always belongs to that epic.

# Technical Context

The create dialog in `app.js` (`openCreateDialog`) builds `meta` from the chosen template, or a bare type, and calls `store.addItem`; the pre-fill is set there. The editor header is `_header` in `ui/editor.js`. Cards render in `_renderCard` in `ui/board.js`, next to the existing parent breadcrumb.

# Requirements

- Setting `parent` on create goes through the normal `addItem` path; no other file is written.
- The marker is informational only; it does not change status or ordering.

# Implementation Notes (decisions taken, 2026-09-29)

The outside-blocker marker reads both sides of a dependency: the card's `depends_on` and any item that names the card in its `blocks` (the demo's BUG-000001 → STORY-000002 is recorded only on the blocker's side). "Outside" means not the epic or one of its members, so other filters never create markers. `Store.newItemParent(type)` decides the pre-fill; the create dialog shows the parent the new item will get. "Focus on board" is keyed on the saved record's type and closes the floating editor first, since the modal covers the board.
