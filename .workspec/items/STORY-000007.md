# Summary

Knowledge about fields is spread across `core/parser.js`, `ui/editor.js`, `core/model.js` and a `coerce()` helper that guesses types from text. Introduce one schema table that the form, coercion, validation and sorting all read, and let `board.yaml` extend it.

# Business Context

PROMPT.md section 13 asks for custom metadata fields "without modifying core logic". Today that is impossible, and the text-shape coercion silently changes field types on save.

# Technical Context

Sketch from docs/REVIEW-2026-09.md section 1.2 A7:

```js
const FIELDS = {
  id:       { type: 'string', required: true, readonly: true },
  title:    { type: 'string', required: true },
  status:   { type: 'enum', required: true, values: (model) => model.workflow },
  priority: { type: 'enum', values: ['critical','high','medium','low'], rank: {...} },
  estimate: { type: 'number' },
  labels:   { type: 'list' },
  created:  { type: 'date', required: true, readonly: true },
};
```

# Requirements

- `core/schema.js` as the single field table; existing constants become derived exports so call sites keep working.
- Editor widgets and coercion keyed on schema type (`ui/editor.js:301`, `:405`).
- `updated` management in `saveItem` (`state/store.js:143`).
- `settings.fields` and `settings.card_fields` support.

# Implementation Notes

Depends on A1 because the round-trip guard determines which items may be form-edited at all.

# Risks

Changing coercion alters what gets written for existing free-text fields; cover with fixtures before switching.
