# Summary

`nextId` returns `max(existing) + 1` computed from the files in the local checkout. Two working copies that each create an item before syncing produce the same ID. The affected unit is the working copy, not the person: one engineer on a PC and a Mac collides with themselves.

# Steps to Reproduce

1. Clone the repository twice (or on two machines) and create a branch in each.
2. In clone A, create a story from the board; it is assigned STORY-000014.
3. In clone B, create a different story; it is also assigned STORY-000014.
4. Merge both branches into main.

# Expected Behavior

Both items keep distinct, immutable IDs and merge cleanly. If a collision does slip through, validation fails before the merge lands.

# Actual Behavior

Git reports an add/add conflict on `items/STORY-000014.md`. Resolving it requires renumbering one item by hand, renaming its file and finding every reference to it, which SKILL.md tells agents never to do. A rebase or squash resolved with "take theirs" drops one item silently, and nothing in the app or repository detects two files claiming the same ID or references pointing at nothing.

# Technical Context

Constraints: SPEC.md section 7.2 (six zero-padded digits, unique, immutable, filename equals ID), goal G5 (minimize merge conflicts), SKILL.md ("do not renumber work items"), PROMPT.md section 15 (no git integration in the app).

Agreed design, per docs/REVIEW-2026-09.md section 3 (per-clone allocator blocks, evaluated against per-author blocks and a per-computer postfix, both rejected):

- Layer 1, prevention: every clone owns a numeric block per type. The block number lives in the git-ignored `config/user.local.yaml`, which the spec already makes per clone; claimed blocks are recorded in a committed registry `config/id-blocks.yaml`. Block 0 is the legacy range, so adoption needs no renumbering.
- Layer 2, detection: uniqueness and registry checks in `loadRepository`, plus `tools/validate-workspec.js` for pre-commit hooks and CI on the pull-request merge commit.
- Layer 3, repair: `tools/renumber.js` with reference rewriting; policy is to renumber only the side that has not reached main.

# Implementation Notes

Configuration sketch:

```yaml
# config/board.yaml
id_allocation:
  strategy: block          # sequential (default) | block
  block_size: 1000

# config/id-blocks.yaml
blocks:
  - { block: 1, owner: rdagum, label: windows-pc }
  - { block: 2, owner: rdagum, label: macbook }

# config/user.local.yaml (git-ignored)
handle: rdagum
id_block: 2
```

`nextId` keeps its signature and gains an options object; with `block` unset it is unchanged. The validator and renumber tools reuse the module loader from STORY-000003, so they can never disagree with the board's own parser. Indexing items by ID in `loadRepository` is shared with STORY-000010 (reference validation). Item creation logic moves to `core/factory.js` in STORY-000005; land the block-aware allocation there if that story ships first.

Suggested order: `nextId` and tests, load-time validation, config and registry parsing, create-dialog claim flow, validator CLI and hook docs, renumber CLI, SPEC.md and SKILL.md updates.

# Implementation Notes (decisions taken, 2026-09-04)

- Allocation logic lives in a new pure module `core/allocation.js` (loaded between `core/parser.js` and `core/model.js`), not in `app.js`, so the board, the tests and the CLIs share one implementation; STORY-000005 can move `createItem` into `core/factory.js` and keep calling `allocateId(model, type)`. `nextId` keeps its signature and gains `{ block, blockSize }`; it now also throws when the six-digit range itself is exhausted instead of returning a seven-digit ID.
- The registry uses one flow mapping per line (`- { block: 1, owner: rdagum, label: windows-pc, claimed: 2026-09-04 }`), so concurrent claims conflict in Git instead of merging silently. `utils/yaml.js` gained flow-mapping parsing for this; like flow sequences, a flow mapping inside an item's front matter is re-serialized in block form on a metadata save.
- "Items from another allocator" cannot be told apart from the owner's own items by range alone, so each registry entry carries an optional `claimed` date written by the claim flow: an item inside a claimed block whose `created` precedes `claimed` is reported. Block 0 is reserved for the legacy sequential range and cannot be claimed.
- Filename/ID mismatch is now an error in `validateItem` (the round-trip tests parse fixtures under their declared ID). `loadRepository` builds `model.itemsById` and runs `validateRepository`; cross-file problems are attached to the records (card badge, editor) and to `loadErrors` (sidebar notices) with a `code`, and the CLI de-duplicates when printing.
- Claiming is a store mutation (`Store.claimIdBlock`) that appends to the registry and patches `user.local.yaml` in place with line-level edits, never a re-serialize, so comments and unrelated keys in either file survive.
- `tools/lib.js` holds the Node filesystem adapter (same interface as `core/filesystem.js`) so both CLIs load the repository with the unmodified browser modules via `test/load.js`. `renumber.js` writes the new file and the reference updates before deleting the old file, so an interrupted run leaves a duplicate that the validator catches rather than a missing item. `--dry-run` and `--dir` were added; archived items are not rewritten.
- Hook and CI: `.githooks/pre-commit` validates the staged `.workspec` tree via `git checkout-index`; `.github/workflows/validate-workspec.yml` runs `node --test` and the validator on push and on the pull-request merge commit.
- Definition-of-done manual tests were run as a scripted simulation with a bare origin and three clones (item files written through `allocateId` + `serializeItem`, the same path as the dialog): different blocks merged with no conflict and both items survived; the same block produced an add/add conflict, a keep-both resolution failed validation with the duplicate-ID error, and `renumber.js` on the unmerged side repaired it. The dialog's claim flow has unit coverage through the store but still wants a click-through in the browser before this is closed.
- This repository now uses `strategy: block`; blocks 1 (windows-pc) and 2 (macbook) are claimed in `config/id-blocks.yaml`, and this clone's `user.local.yaml` holds `id_block: 1`. The macbook clone needs `handle: rdagum` / `id_block: 2` in its own local file. Existing items stay in block 0; the next STORY created here is STORY-001001.
- Found during the simulation: a registry left with Git conflict markers parsed "successfully" because the YAML engine skips lines without a colon. `parseItem` and `parseConfig` now report unresolved `<<<<<<< ` / `>>>>>>> ` markers as an error (a bare `=======` is left alone, it is also a Markdown heading underline), so a half-merged registry or item fails validation.
