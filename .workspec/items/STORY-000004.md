# Summary

Every store emit rebuilds the entire board and sidebar, including on each search keystroke and each toast. Items are also read from disk one at a time. Neither meets the PROMPT.md section 8 target of 2,000 items with a board in under one second.

# Business Context

The performance requirement is explicit in the reference implementation brief. Large repositories are the point of a Git-native tracker.

# Technical Context

`app.js:58-63` replaces the board on every emit; `state/store.js:95` re-scans all items in `facets()`; `core/model.js:124-131` awaits each file sequentially. See docs/REVIEW-2026-09.md section 1.2 A4 for the ordered plan.

# Requirements

1. Memoize derived selectors.
2. Debounce the search box (`ui/sidebar.js:45`).
3. Keyed card reconciliation in `BoardView` using `record.version` (from STORY-000002).
4. Only if profiling still shows a problem: slice the state into `items`, `selection`, `filters`, `message` events.
5. `Promise.all` over batches of about 32 files in `loadRepository`.

# Implementation Notes

Do the cheap steps first and measure after each; virtualization is out of scope unless measurements demand it.

# Risks

Reconciliation bugs can leave stale cards on the board; keep a full-rebuild fallback path for the error state.
