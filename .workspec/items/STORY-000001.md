# Summary

The YAML engine promises to preserve everything but fails silently: stray indentation truncates the rest of the front matter, trailing comments and flow mappings are absorbed into string values, backslashes double on every save, and `|` gains a trailing newline. Because the editor re-serializes from the parsed object, each of these becomes a lossy write. Make the engine either lossless or loud.

# Business Context

SPEC.md sections 15 and 17 require "save without data loss"; PROMPT.md section 11 requires "never silently fail". Any lossy save undermines the core promise of a Git-native tracker: the file is the record.

# Technical Context

See docs/REVIEW-2026-09.md section 1.2 (A1) and section 4, findings 1, 4, 5, 9 and 10. The findings marked *confirmed* were reproduced under Node by loading `utils/yaml.js` with a `window` shim.

# Requirements

- Strict parse: throw in `parseMapping` on unexpected indent (`utils/yaml.js:200`) and on non key/value lines (`utils/yaml.js:204`).
- Symmetric scalar escaping between `parseScalar` and `serializeScalar`.
- Strip unquoted trailing comments; handle or reject flow mappings.
- Emit `|-` when a multi-line value does not end in a newline.
- `patchScalarLine` must anchor the key at column 0 so a nested `agent.status` is never patched instead of the top-level `status`.
- Round-trip guard on load producing `record.lossy`; editor and store honour it (raw-only editing, verbatim save).
- Optional: preserve standalone comment lines as ordered pseudo-entries so they survive a metadata save.

# Implementation Notes

Depends on the test harness (STORY-000003) so each fix ships with a fixture. Keep the browser code path unchanged: no build step, no dependencies.

# Risks

Making the parser strict may surface errors in existing repositories that used to load "successfully" with truncated metadata. That is the desired outcome, but the error messages must point at the offending line.
